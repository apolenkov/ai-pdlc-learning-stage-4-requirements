# Сопровождение метарепозитория

Общая `main` — универсальный эталон R4, а не готовая личная история ученика. Изменяйте её через maintenance-ветку и review. Personal import-base готовится отдельно по [инструкции организатора](docs/organizer-stage-4.md), публикуется отдельной веткой и не сливается обратно как учебный результат.

## Граница ролей

- Организатор получает полный planning SHA ученика, переносит из его Git tree весь `openspec/specs/` и все активные Changes, формирует manifest, проверяет отдельный service pin и публикует personal import-base. Ученику передаётся полный договор: URL метарепозитория, branch, import-base SHA, planning SHA, service SHA и review reference.
- Ученик создаёт fork с копированием всех веток, клонирует свой fork в `sdd-guide-credit-calculator-stage-4-requirements`; `origin` остаётся fork. Upstream используется только для fail-closed чтения отсутствующей import-base, без записи, force и подстановки `main`.
- Полный `setup-analysis-workspace` проверяет requirements, создаёт либо проверяет соседний `sdd-guide-credit-calculator-stage-4-code` на service pin, выполняет setup/check:code, Store doctor, два реальных bootstrap и check:store.
- Отсутствующая Store-запись может быть создана явным запросом полной подготовки. Конфликтующий root не заменяется без отдельного подтверждения точных старого и нового путей; существующая code-папка не переключается и не перезаписывается.
- После чистого отчёта skill ученик продолжает основной маршрут: шаг 3 «Изменение в OpenSpec» (обязательный) перед шагами 4–5; его активные Changes входят в source. Code checkout остаётся detached до принятия требований и отдельного разрешения на реализацию.

Manifest описывает фактические импортированные Changes из planning source; их состав зависит от реально пройденных шагов. Main specs источника могут быть пусты. Не добавляйте фиктивный baseline и не закрепляйте SHA планирования в `services.lock.yaml`.

## Проверка эталона

Перед commit выполните:

```bash
npm run check
git diff --check
git diff
git status --short
```

Тесты должны проверять source-driven inventory и инварианты, а не фиксированное число Changes, файлов, строк матрицы или вхождений текста. Отдельно различайте fixture-тесты и реальные bootstrap подготовленной personal base.

MTP `grill-with-docs` и зависимости закреплены в `.agents/mtp-skills.lock.json`. Не редактируйте оригинальные MTP и сгенерированные OpenSpec skills вручную. Обновление MTP через `npm run skills:update` требует отдельного решения о версии и полном SHA.

Подготовка, публикация ветки, planning MR, одобрение и будущий Apply — разные действия. В учебных шагах 4–5 одобрение владельца продукта относится к последней версии diff; аналитик и техлид оставляют замечания, архитектора приглашают через @. Локальная проверка не подтверждает публикацию, реализацию функций или человеческую приёмку.
