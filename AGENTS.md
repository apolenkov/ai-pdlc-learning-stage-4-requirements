# Правила метарепозитория

## Роли и ветки

- Владелец эталона меняет общие инструкции и автоматизацию только в maintenance-ветке с отдельным review.
- Организатор готовит и публикует personal import-base из полного Git SHA ученика. Он не занимает локальную рабочую папку ученика и не выдаёт неподготовленную `main` за личную историю.
- Место в курсе: подготовка → шаг 1 «Требования в Git» → шаг 2 «Проверяем и согласуем» → шаг 3 «Изменение в OpenSpec» (обязательный) → шаг 4 «Команда продукта» → шаг 5 «Контекст продукта» → 6а или 6б → «Практикум разработки»; этот репозиторий — шаги 4–5. Ученик создаёт корпоративный fork с копированием всех веток, клонирует из него опубликованную `course/<LOGIN>/stage-4-import-base` и работает в `course/<LOGIN>/stage-4-amount-limits`; `origin` всегда указывает на fork. Planning MR направляется в personal import-base внутри fork, не в upstream и не в общую `main`.
- Одобрение по текущему diff даёт владелец продукта: он нажимает Approve. Аналитик и техлид оставляют замечания в MR/PR. Поскольку шаги 4–5 в этом примере подключают внешнюю систему банка, архитектора приглашают через @: он пишет замечания (и `design.md`), но одобряет по-прежнему владелец продукта. После новых коммитов владелец продукта одобряет последнюю версию заново. Автор не одобряет свой запрос. ИИ и автоматическая проверка одобрение не заменяют.

Требования, планы и задачи принадлежат этому метарепозиторию. В новом комплекте R4 код и runtime-тесты принадлежат отдельному `ai-pdlc-learning-stage-4-code`. Аналитическая ступень не разрешает Apply. После отдельного разрешения на реализацию агенту явно задают оба рабочих root и границы правок: код в сервисе, задачи после проверки в Store. Указатель Store сам не даёт доступ к соседней папке. Существующие личные пары и их service pins не заменяются автоматически.

Репозиторий хранит контекст продукта и спецификации, но не код сервиса. Не добавляйте токены, персональные данные, корпоративные документы, dependencies или `.workspace/`.

## Контекст перед изменением

Прочитайте `CONTEXT.md`, `product.yaml`, `services.lock.yaml` и `openspec/config.yaml`.

До успешной поздней точки входа разберите запрос и замыслы: `request-and-answers.md` — источник фактов упражнения, `intent-template.md` — общий шаблон, `examples/clear-calculation-result.md` — предоставленный пример, а `intents/intent-2-credit-limit.md` — отдельный запрос R4. В личной истории ученика один актуальный файл `intents/clear-calculation-result.md` проходит через R1–R3; он не является второй копией примера из этого шаблонного репозитория.

В personal import-base дополнительно прочитайте:

- `docs/course/planning-provenance.json`;
- `docs/course/stage-3-transfer.md` и `requirements-traceability.md`;
- весь `openspec/specs/`;
- каждый Change из `imports.activeChanges` manifest.

Импорт содержит фактически существующие активные Changes переданного source. Main specs могут не содержать предметной spec. Не придумывайте исходное состояние, дополнительные имена Changes, число файлов, сценариев или задач. Все задачи реализации импортированных Changes должны оставаться незавершёнными до отдельного Apply.

## Порядок входа ученика

1. Получить у организатора `<META_REPOSITORY_URL>`, `IMPORT_BASE_BRANCH`, `IMPORT_BASE_SHA`, `PLANNING_SHA`, `SERVICE_SHA` и `REVIEW_REFERENCE`; создать fork с копированием всех веток и клонировать personal import-base из fork в `ai-pdlc-learning-stage-4-requirements`.
   Без организатора данные организатора не требовать: ученик собирает тот же договор по README, подраздел «Самостоятельно, без организатора». `META_REPOSITORY_URL` — исходный репозиторий курса `https://github.com/apolenkov/ai-pdlc-learning-stage-4-requirements.git`, `IMPORT_BASE_BRANCH` — личная `course/<LOGIN>/stage-4-import-base` в fork, `IMPORT_BASE_SHA` — SHA `course/example/stage-4-import-base` в исходном репозитории курса по `git ls-remote`, не в fork; `PLANNING_SHA` — `source.commit` из `docs/course/planning-provenance.json`, `SERVICE_SHA` — `commit` из `services.lock.yaml`, `REVIEW_REFERENCE` — ссылки из `docs/course/stage-3-transfer.md` или `pending`.
2. Маршрут с организатором: если ветка не скопировалась, применять fallback только после доказанного отсутствия ветки в fork и точного совпадения upstream SHA с `IMPORT_BASE_SHA`; не писать в upstream, `main` и не использовать force.
3. Открыть requirements root в VS Code и в чате агента Kilo получить Git root и прочитать целиком именно `<ABSOLUTE-GIT-ROOT>/.agents/skills/setup-analysis-workspace/SKILL.md`. Одноимённый глобальный или любой другой skill не выполнять. Навыки OpenSpec лежат в корне репозитория в универсальном `.agents/skills` и читаются Kilo автоматически.
4. Полный project skill проверяет requirements base/SHA, создаёт либо проверяет соседний `ai-pdlc-learning-stage-4-code` на точном service pin, выполняет setup/check:code, безопасно связывает Store, дважды запускает bootstrap и проверяет `check:store`. Существующие папки и конфликтующий Store root не заменяются без отдельного подтверждения точных путей.
5. Только после чистого отчёта создать аналитическую ветку, пройти original `grill-with-docs`, при оставшейся существенной развилке OpenSpec Explore, затем OpenSpec Propose и человеческое review.

Setup skill не создаёт Change или рабочую code-ветку, не продолжает workflow автоматически и не разрешает Apply. Fixture-тесты из `npm run check` не считаются двумя реальными bootstrap.

## Подготовка OpenSpec Change

1. Прочитайте исходный intent, запрос R4 и подтверждённые ответы. Используйте original MTP `grill-with-docs` до явного подтверждения общего понимания.
2. Если после grill остаётся существенная развилка, используйте OpenSpec Explore; иначе переходите к OpenSpec Propose.
3. Не придумывайте отсутствующие факты: оставляйте их открытыми вопросами и продолжайте интервью до явного подтверждения общего понимания.
4. OpenSpec Propose создаёт полный набор планирования и останавливается на человеческой проверке.
5. Apply запускается отдельно только после принятия; автоматический переход от Propose запрещён.
6. Новый `limit-credit-amount` явно зависит от каждого фактически импортированного активного Change.
7. Если прежний успешный сценарий на 101 ₽ конфликтует с минимумом 10 000 ₽, спросите пользователя о замене новой delta на 10 001 ₽ / 0% / 2 месяца. Не выбирайте и не переписывайте унаследованный файл молча.

Сверяйте итоговый договор по фактическим файлам: различайте незатронутые сценарии, явно заменённые ожидания и новые сценарии. Не подставляйте заранее заданные количества; источником являются Git tree, manifest и сами артефакты.

OpenSpec — единственный источник спецификации. MTP `to-spec` не используется. Не создавайте локальный process skill, пересказывающий MTP или OpenSpec. Apply, archive и sync на аналитической ступени запрещены; код сервиса не меняется.

## Store и снимки

- Store ID — `sdd-credit-calculator-product-meta`; для чтения и validation указывайте `--store sdd-credit-calculator-product-meta` и сначала подтверждайте root.
- Происхождение планирования хранит отдельные repository/SHA/inventory/hash. `services.lock.yaml` содержит независимый service pin; SHA планирования нельзя записывать как версию приложения.
- `.workspace/planning/stage-3` и `.workspace/services/credit-calculator` — read-only проверочные снимки, а не места редактирования planning или кода.
- Store и bootstrap не выполняют commit, push, merge, регистрацию или переназначение Store.
- Для будущего Apply разработчик использует отдельный рабочий checkout сервиса.

Изменения эталона должны пройти `npm run check`, `git diff --check` и человеческое review. В учебных шагах 4–5 одобрение текущего diff даёт владелец продукта; аналитик и техлид оставляют замечания, архитектора приглашают через @: сценарий затрагивает систему банка. Сохраняйте исходный exit status команд; не подменяйте его результатом `grep`, `tail` или pipeline.
